# Requirements: Search & Filtering (Client Discovery)

Last Updated: 2026-08-14
Branch: feature/2026-08-14-search-filtering
Status: Planned

Context: Turns roadmap Phase 4 (Search & Filtering) into executable requirements,
reconciled with the current codebase. The roadmap brief predates the actual search
surface: the backend already exposes `GET /workshops/` with name + bounding-box
location filters, while the client search page ignores the backend entirely and
queries OpenStreetMap's Overpass API. There is no per-workshop service catalog —
the `services` table holds service orders, and schedules carry only a 4-value
request type. This phase (1) adds a `workshop_services` catalog so workshops
declare what they offer, (2) extends the backend search with min-rating,
service-type filtering, sorting, and real Haversine distance, and (3) rebuilds the
client search page on the backend API. Follows the multi-tenancy foundation
(`specs/2026-05-30-multi-tenancy-foundation`), the reviews phase
(`specs/2026-08-14-reviews-ratings`), and the four-layer backend architecture
documented in `CLAUDE.md`.

## 1. Scope

### In Scope

- `workshop_services` catalog: new model/table (workshop × service type, unique
  pair), Alembic migration, and a WORKSHOP-only manage endpoint. The catalog
  reuses the schedule request-type taxonomy (`ServiceRequestType`:
  `manutencao`, `reparo`, `inspecao`, `outro`) — the only service taxonomy in the
  codebase.
- Workshop UI to manage the catalog: new "Serviços Oferecidos" sidebar page
  (checkbox list → save) at `/workshop/services-offered`.
- Backend search extension on the existing `GET /workshops/`: `min_rating`,
  `service_types` (CSV, OR semantics), `sort` (`distance` | `rating` | `reviews`),
  radius cap, and a new `WorkshopSearchItem` response carrying `distance_km`,
  `service_types`, and `ratings_count`.
- Haversine distance util in `src/utils/workshops.py` (SQL bounding-box prefilter
  + exact distance in Python).
- Client search page rebuild: filter sidebar + `WorkshopCard` list + Leaflet map,
  driven by the backend API (Overpass query removed), with pagination and
  Portuguese UI copy.
- Backend test slice, frontend type check + Vitest slice, `CHANGELOG.md` entry,
  and roadmap Phase 4 status update.

### Out of Scope

- `is_active` on workshops / the roadmap's "only active workshops returned" test —
  user-confirmed defer; no activation concept exists in the product.
- PostGIS / Elasticsearch / saved searches (roadmap Phase 9).
- A separate `/workshops/search` route — the existing `GET /workshops/` is
  extended (same convention call the reviews phase made for `/workshop-ratings`).
- Changes to the workshop detail page (`workshop-page.tsx`); showing offered
  services there is a follow-up.
- Map pins sourced from OpenStreetMap data.
- Infinite scroll / virtualized lists.

## 2. Functional Requirements by Phase

### Phase 1 — Backend catalog (TG1)

- `src/models/workshop_service.py` — `WorkshopService` model:
  - Table `workshop_services`; `id` int PK; `workshop_id` FK → `workshops.id`
    (CASCADE); `tenant_id` FK → `tenants.id` (not null, index) — the workshop's
    tenant, for row-level scoping; `service_type` String(20) not null.
  - `UniqueConstraint("workshop_id", "service_type")` and composite index
    `("tenant_id", "id")` (mirror the other models' index naming).
- Alembic migration autogenerated with `make migrations msg="add workshop_services
  catalog"`; verified to apply clean at head.
- `src/schemas/workshop_service.py`:
  - Reuse `ServiceRequestType` from `src/schemas/schedules.py`.
  - `WorkshopServiceRead` — `id`, `workshop_id`, `service_type`
    (`from_attributes`).
  - `WorkshopServicesUpdate` — `service_types: list[ServiceRequestType]`
    (bulk-replace payload).
- `src/repositories/workshop_service.py` — free `repo_*` functions, commit/refresh
  in the repo: `repo_list_workshop_services(db, tenant_id, workshop_id)` and
  `repo_replace_workshop_services(db, tenant_id, workshop_id, service_types)`
  (delete-then-insert in one transaction). Every function requires an explicit
  tenant id and raises when missing (mirror the schedules/ratings repository
  contracts).
- `src/services/workshop_service.py` — `WorkshopServiceService(db)`: resolves the
  caller's workshop via the tenant-scoped workshop repository and delegates;
  `ValueError` when the workshop is missing.
- `src/api/routes/workshop_services.py`, registered in `src/routers.py`
  (`prefix="/workshop-services"`, `tags=["workshop-services"]`):
  - `GET /workshop-services/me` — WORKSHOP; own catalog list.
  - `PUT /workshop-services/me` — WORKSHOP; bulk-replace
    (`WorkshopServicesUpdate`); `200` with the resulting list.
  - Role gating inline (mirror `_require_role` in `schedules.py` routes): wrong
    role → `403`; `ValueError` → `404`.

### Phase 2 — Backend search (TG2)

- `src/utils/workshops.py` — `haversine_km(lat1, lon1, lat2, lon2) -> float`
  (Earth radius 6371.0).
- `src/schemas/workshop.py` — `WorkshopSearchItem`: `id`, `name`, `description`,
  `latitude`, `longitude`, `rating_avg`, `phone`, `address`, `city`, `state`,
  `logo_url`, `distance_km: float | None`, `service_types: list[str]`,
  `ratings_count: int`. Deliberately excludes `tenant_id`, `user_id`, `email`,
  and opening-hours fields — the public directory shape for client discovery.
- Extend `repo_search_workshops` (and the service/route passthrough):
  - `min_rating: float | None` — filter `Workshop.rating_avg >= min_rating`
    (Query `ge=0, le=5`).
  - `service_types: str | None` — CSV of enum values; unknown value → `400`;
    OR semantics via join on `workshop_services` (workshop matches if it offers
    any of the requested types).
  - `sort: str` — `distance` (default when `lat`/`lng` present), `rating`
    (default otherwise), `reviews`. `sort=distance` without `lat`/`lng` → `400`.
    `rating` = `rating_avg` desc; `reviews` = `ratings_count` desc; `distance` =
    ascending.
  - `radius_km` — Query(10.0, `ge=0`, `le=100`) cap.
  - `ratings_count` via correlated subquery: count of `workshop_ratings` rows
    where `workshop_tenant_id == Workshop.tenant_id`.
  - `distance_km` computed per row with `haversine_km` only when `lat`/`lng`
    were provided; `None` otherwise. Sorting by distance happens after the
    bounding-box prefilter (exact distance in Python).
  - Pagination stays `skip`/`limit` (existing convention).
- Route changes in `apps/backend/src/api/routes/workshops.py`: new Query params,
  `response_model=list[WorkshopSearchItem]`.

## 3. Cross-Cutting Requirements

### 3.1 Tenant isolation vs. public discovery (critical)

- `workshop_services` writes are tenant-scoped: every `repo_*` requires the
  workshop's tenant id; a workshop can only manage its own catalog. Requests
  scoped to any other tenant return empty/`None` (never leak).
- Workshop search is the deliberate cross-tenant read path (client discovery,
  already the behavior of `repo_search_workshops` and
  `repo_get_workshop_by_id_any_tenant`). It must NOT filter by the caller's
  tenant, and `WorkshopSearchItem` must not expose tenant ids or workshop-owner
  user ids.

### 3.2 Role matrix

- WORKSHOP: manage own catalog (`GET`/`PUT /workshop-services/me`).
- CLIENT: search only (`GET /workshops/`).
- Any authenticated role may search; catalog management by a non-WORKSHOP role →
  `403`.

### 3.3 Service-type validation

- `service_types` query values and catalog writes are validated against the
  4-value enum; unknown values → `400` (never silently dropped).

## 4. Technical Decisions

1. **Extend the existing `GET /workshops/`** instead of adding a new
   `/workshops/search` route — matches the reviews phase's naming reconciliation
   and avoids a duplicate discovery surface.
2. **New `workshop_services` table** with unique `(workshop_id, service_type)`;
   taxonomy = the 4 schedule request types (the only service taxonomy in the
   codebase). No free-text types.
3. **OR semantics** for multi-service filtering.
4. **Haversine in `src/utils/workshops.py`** per the `utils/<domain>.py`
   convention; SQL bounding box prefilter (existing behavior) + exact distance in
   Python; `distance_km` only when `lat`/`lng` are provided.
5. **`WorkshopSearchItem` search-only schema** — keeps `WorkshopRead` (profile
   management contract) untouched and omits tenant/owner identifiers.
6. **Sort set** — distance (default with coords) / rating (default without) /
   reviews (ratings count desc); `sort=distance` without coords → `400`.
7. **`PUT /workshop-services/me` bulk-replace** — matches the checkbox UX, is
   idempotent, and avoids per-row delete bookkeeping.
8. **No `is_active`** this phase (user-confirmed); the roadmap's "only active
   workshops" test is dropped and revisited when workshop activation exists.
9. **Radius capped at 100 km** to bound the prefilter/distance computation.
10. **UI copy PT; specs EN** — the project convention from the reviews phase.

## 5. Success Definition

Ready for merge when:

- a workshop can declare its offered service types on a dedicated page and the
  catalog persists across reloads;
- `GET /workshops/` filters by min rating and service types, sorts by
  distance/rating/reviews, and returns distance, offered types, and ratings count;
- the client search page lists app workshops from the backend with filters,
  sorting, pagination, and map pins — no Overpass calls;
- catalog writes are tenant-safe and search remains public-read (no tenant ids
  leaked in responses);
- backend test slices + full suite pass, `npm run check` passes, the Vitest slice
  passes, and `alembic upgrade head` applies clean with the new revision;
- `CHANGELOG.md` is updated, roadmap Phase 4 status is updated, and the
  `validation.md` gates pass with the user having reviewed the result.
